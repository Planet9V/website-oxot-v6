# OXOT Layout Style References

**New to this system? Start with [`OXOT_README.md`](./OXOT_README.md) first.**

**Status: durable reference — Task A**, the visual/structural layout-pattern research the original agent-creation instruction called for. Distinct from `OXOT_Component_Inventory.md`'s "Standard page layout archetypes" (which covers *content-purpose* types). This file covers *how a section is visually structured* — but structure alone isn't the point. **Anyone can build a bento grid. The bar here is that a page built from these should be recognizable as OXOT with the logo cropped out** — because the pattern itself is drawn from the product's own real mechanics (the Twin's attack-path data, the Seldon Engine's 7 physical layers, IEC 62443 zone/conduit language), not borrowed wholesale from a generic SaaS block library.

Each pattern below states its generic structural lineage (so it's traceable to real, cited research — see Sources) and then the specific OXOT execution, which is the actual design work.

## OXOT's shape language — 8 signature patterns

### 1. Consequence Cascade Hero
*(lineage: split-screen hero)*

Not "headline left, screenshot right." The right pane **is the product's own mechanic, run once, small, on load**: a thin `--signal-blue` line draws itself from an entry-point node (a labeled remote-access chip) through 2-3 intermediate asset nodes to a highlighted target. **Headline and subhead render immediately at paint, never gated behind the animation** (fix, flagged by independent Fable review — the ~2.5s total sequence was flagged once before but never actually restructured; a single 2.5s animation is itself out of the Foundation Spec's 300-500ms diagram tier). The path is instead **N discrete per-segment draws, each within the 300-500ms diagram budget** — node-to-node, not one continuous 2.5s sweep — so every individual motion stays in spec even though the full sequence still takes a few seconds to complete. Each node lights as its segment finishes; the final node pulses once. The left-pane copy (`blur-fade`, ~80ms stagger) appears *exactly when the node it describes lights up*, but the headline/subhead are never part of that gating.

- **Data:** driven by one real `TwinScenario.attackPathIds` record, not a fabricated illustration — this is Twin Explorer output shrunk to hero scale, not decoration that resembles it.
- **Tokens:** path = `--signal-blue` until the path resolves. **Fix, flagged by independent Fable review:** the endpoint originally used `--signal-amber`, but amber is defined as *proposed/pending decision* — painting an already-breached target amber reads as "proposed remediation," not "impact." The endpoint instead stays `--signal-blue` with a `--signal-amber`-colored *label chip* naming the specific consequence, keeping the path itself token-consistent while still surfacing the consequence semantically — never green, since nothing has been validated-closed yet at first paint.
- **Accessibility:** a visually-hidden text summary states the full path in one sentence ("Vendor remote access → engineering workstation → dosing PLC → disinfection consequence") so the animation is decorative, not load-bearing. `prefers-reduced-motion` jumps straight to the lit end-state.
- **Mobile (fix, flagged by independent review):** the split-pane structure doesn't survive a narrow viewport as-is. On mobile, stack per Mobile Rules' mandatory order — text block first, then the path visual beneath it, tap-to-play instead of auto-play (auto-playing a 2.5s animation on load competes with page-load attention on a slow connection).
- **Claim boundary (fix, flagged by independent review):** "Illustrative scenario — no customer data" must be visibly printed on the hero itself, not just implied — the pattern uses a real `TwinScenario` record shape, so the disclaimer is load-bearing, not decorative.
- **Pane balance (floor rule, added 2026-08-24, Industries scope; mechanism tightened the same day by an independent Opus second pass):** the two panes must read as visually balanced, not copy-column-short-beside-diagram-tall. The mechanism has to actually *relate the two heights*: put both panes in the same CSS grid row, or in a flex row with `items-stretch`, so the shorter pane's box is sized from the taller one.
  - **`items-center` is not that mechanism.** Centring a short copy pane inside a tall row is the defect being fixed, just centred — it relates nothing. It is permitted only as an alignment choice *after* the ratio below is already met by content, never as the height-relating mechanism itself. (The first draft of this rule offered `items-center` as an accepted alternative; that made the rule self-defeating and is withdrawn.)
  - **A hardcoded `min-h-[...]` measured off the diagram is a last resort**, and must name the breakpoint it was measured at. This site renders bilingual copy (`pick(..., locale)` throughout the real components), so a height tuned to one locale's copy length breaks in the other — prefer the shared-grid-row form, which has no such coupling.
  - **Ratio:** neither pane's rendered height may exceed roughly 1.5x the other's, measured on the two panes of the shared row at the primary desktop breakpoint. This is deliberately tighter than `OXOT_Composition_Rules.md`'s site-wide 2x sibling-balance floor, and governs here.
  - **Stretching an empty box does not pass.** If the copy pane needs a stretch container to reach height, it does not have enough content: add real content, or reduce the diagram pane's height. Same failure mode Pattern 2's Proposed-control rule names — bare chrome sized to fill space.
  - **Desktop only.** Once the pattern stacks to a single column on mobile the panes are no longer siblings in a row, and the ratio does not apply.
  - **Targets a real, named defect, still live as of 2026-08-24:** `water-wastewater-1`'s `WaterHero.tsx` puts copy at `lg:col-span-5` beside the diagram at `lg:col-span-7` inside a plain `grid gap-12 lg:grid-cols-12` — no `items-*`, no min-height, no height coupling of any kind.
- **Serves:** Home Hero + Twin Explorer (Foundation Deliverable 1).

### 2. Three-Gate Ledger
*(lineage: before/after comparison slider — REPLACED 2026-08-24, see below)*

**Replaced, not merely fixed.** The original "Baseline / Virtual-Control Reticle" was a two-pane slider claiming to fulfill Foundation Deliverable 3, but §7's required panels are **three**: Baseline, Proposed control, Decision output — a two-pane control structurally cannot render the third (recommended sequence, evidence needed, implementation window, validation condition, responsible role has nowhere to go). Two independent AI review rounds patched the Reticle's accessibility problems without ever catching that the pattern *shape itself* couldn't express the deliverable; the `stage_1_opus` independent research pass caught it directly by re-deriving from §7's own table (`stage_1_opus/comparison_vs_existing_system.md` §2.1(b)). The crosshair-reticle P&ID idiom and the enumerated, individually-focusable delta list were genuinely good and survive into the new structure below.

**Three unequal columns over one shared canvas**, sharing a single diagram above them rather than each column owning its own visual:

1. **Baseline** (widest, rendered `--signal-slate`) — "as documented": entry point, intermediate systems, target asset, consequence chain, known constraints.
2. **Proposed control** (`--signal-amber`) — the control inserted in the model: which routes it affects, which required flows it preserves, the residual exposure it leaves. The crosshair-reticle idiom (a small circled cross, P&ID convention, not a rounded UI pill) marks the insertion point directly on the shared canvas.
3. **Decision output** (narrowest, densest) — recommended sequence, evidence needed, implementation window, validation condition, responsible role. The panel the two-pane Reticle had no room for.

Every node whose state differs between baseline and the proposed control gets a persistent amber outline on the shared canvas — the discrepancy list below it is real and enumerated, not a bare count.

- **Column-width order — confirmed correct in this spec, violated in a test build (floor-rule note, added 2026-08-24, Industries scope; re-verified against live code the same day by an independent Opus second pass):** this pattern already states Baseline as widest and Decision output as narrowest/densest (see the ordered list above), which makes the requirement a **strict ordering: span(Baseline) > span(Proposed control) > span(Decision output)** — a checkable inequality, not a matter of taste. A 2026-08-24 test Industries page inverted it: `water-wastewater-1`'s `WorkedExample.tsx` renders `lg:col-span-4` / `lg:col-span-5` / `lg:col-span-3`, putting the *middle* column widest, beneath a code comment reading "Unequal by construction, not by accident." **Still unfixed as of this note.** That is an implementation defect against an already-correct spec, not a documentation gap — this file did not need its stated order corrected. Builders: check the three span numbers against the inequality above; don't eyeball relative widths, and don't accept a comment *asserting* the asymmetry is deliberate as evidence that it is — that is exactly the comment this defect shipped under.
- **Proposed control minimum density (floor rule, added 2026-08-24, Industries scope; strengthened the same day by an independent Opus second pass after reading the live implementation):** because Proposed control's content is progressively disclosed, it is structurally prone to rendering emptier than its siblings before a user interacts with it — no rule anywhere in this pattern previously addressed that. Confirmed live: `WorkedExample.tsx` initialises its selection to `null`, so on first paint that column is three bare option buttons and nothing else, standing beside two fully-populated siblings. The first draft of this rule accepted *either* remedy below; that was too weak, because (a) alone does not hold. **(b) is mandatory. (a) is additionally recommended where it fits.**
  - **(b) Fixed supporting copy, always present — required.** The column carries content that does not depend on selection state — what a proposed control is, how its residual-exposure figure is computed, what the crosshair-reticle marker means — sized to occupy real height on its own. Required because a pre-selection is not durable cover: a user can move the selection to a shorter candidate, and a scenario may legitimately carry zero candidate controls, in which case (a) is impossible and only (b) keeps the column from collapsing.
  - **(a) Pre-select the first candidate — recommended.** The disclosed panel is then populated on initial load rather than waiting on interaction. Weigh it against the register's posture, though: on a *decision* surface, a forced default selection can read as OXOT having already picked a control for the customer. Where that reads wrong, or where the radiogroup's semantics argue against a checked-by-default state, (b) alone satisfies the floor.
  - A Proposed control column that is bare chrome with nothing to show until a user acts fails this pattern regardless of its column width.
- **Decision output overflow — collapse its content categories, never widen the column (technique, added 2026-08-26; fixed live 2026-08-25 on both `water-wastewater-2` and `-3`).** This pattern puts the narrowest span and the densest content on the same column by design, which makes one specific failure mode structural rather than accidental: Decision output is simultaneously the *narrowest* of the three columns and, if its evidence groups all render open, the *tallest* — visibly out of proportion in both directions at once. **The numeric sibling-balance floor does not catch it**, and that is the reason to write it down: a height ratio can sit comfortably inside 0.50 while the column still reads as badly imbalanced, because the defect is narrow-and-tall, not short. The fix is to shorten the **default pre-interaction state** — convert each evidence category from an always-open `<dl>` to a collapsed-by-default `<details>`/`<summary>` disclosure, which is also the exact state the balance harness measures. Two properties make this a real remedy rather than a dodge: the mandated span ordering (`Baseline > Proposed control > Decision output`) is untouched, so it cannot be used to quietly widen the narrowest column out of its stated order; and no content is removed, so the density this column is *supposed* to carry survives one interaction away. Do not reach for it on the other two columns — Baseline is the reader's entry point, and Proposed control is already governed by its own minimum-density floor above, where hiding content is the failure rather than the fix. Reference implementation: `ThreeGateLedger.tsx` on `/industries/water-wastewater-2` and `-3` (same component, same change, both pages).
- **Tokens:** slate (baseline/unverified) → amber (proposed control, pending) → green (only once the modelled result actually closes a route, never before). Amber outline on the canvas marks deltas only.
- **Accessibility:** the discrepancy list is a real, enumerated, individually-focusable list ("1. Dosing PLC — firmware version differs. 2. ..."), and **each list item is itself a control that moves focus/highlight to its canvas node** — carried forward from the Reticle's own review history, since AT users reading *about* a delta without a way to reach its canvas node was a real, previously-caught defect. No drag-only interaction anywhere (Mobile Rules bans it outright) — this is why the pattern was replaced rather than patched: a slider is drag-shaped by construction, and no amount of keyboard/touch alternative bolted onto a two-position control changes that the model itself has three states (closed / preserved / residual), which a wipe/slider cannot represent regardless of its accessibility layer.
- **Mobile:** the mandatory stacking order applies (View selector → Canvas → State summary → Evidence drawer → CTA); the three columns stack vertically in Baseline → Proposed control → Decision output order, never side-scrolled.
- **Guardrail:** "Illustrative scenario — no customer data" always visible, not buried.
- **Serves:** Baseline vs Virtual Control (Foundation Deliverable 3) — this pattern *is* that deliverable, matching §7's three-panel structure exactly rather than approximating it in two.

### 3. Asset-Class Bento
*(lineage: bento grid → tiered bands)*

Cells are not generic feature blurbs. Each cell **is one of the 9 real `SystemAsset.type` values** (process-equipment, field-device, controller, hmi, engineering-workstation, network-device, remote-access, safety-function, service). **Redesigned 2026-08-25, superseding the criticality-sized grid described in this pattern's earlier drafts.** The original mechanic sized cells by `criticality` — `critical` assets at `col-span-2 row-span-2`, down to 1×1 for `context` — using cell *area* to encode a 3-tier ordinal value. Independent research commissioned after an owner grade of 5/10 found this the wrong encoding channel: area judgments are unreliable, especially across similarly-shaped rectangles (which a CSS grid produces by construction), while position ranks far higher for encoding ordinal data. The pattern now renders **three horizontal bands — Critical / Important / Context** — with every card inside a band at uniform size. Tier is carried by band position, a visible band label with its item count, and a single-hue rail-intensity step — not by cell area, and not by a second competing accent color. Icons are single-color, line-drawn engineering glyphs (schematic-style, matched to the `--foreground` token) — never filled, never Lucide's default rounded-icon-pack look, which reads as generic SaaS on sight. As of the same rebuild, 6 of the 9 glyphs are sourced from real, MIT-licensed external sets (Siemens iX icons; geometry cross-checked against Equinor's `engineering-symbols`) and redrawn to this pattern's existing stroke idiom — `OXOT_Component_Inventory.md` carries the sourcing/licensing detail; this doc records only the visual contract.

- **Why this can't be a static template:** the bands' actual contents change per industry, because the underlying `SystemAsset` list differs — rail's controller inventory isn't hyperscale's. The pattern is a renderer, not a design.
- **Accessibility:** every card is keyboard-focusable, DOM order matching visual order (WCAG 2.4.3, unchanged by the rebuild); every glyph is paired with a visually-hidden text label plus a screen-reader criticality announcement.
- **No hierarchy fallback needed, by construction.** The retired grid mechanic needed two separate fallback rules — one for too few critical assets (a long tail of identically-sized 1×1 cells), one for too many (multiple competing 2×2 "hero" cells with no single focal element) — because area-encoding breaks at both extremes of a tier's population. Tiered bands have neither failure mode: a band with 1 asset and a band with 8 both render correctly, because band membership, not cell size, carries the signal. Both prior fallback rules are retired outright, not superseded — there is no equivalent case left to handle.
- **Content floor, restated for bands:** every card's description renders in full, unclamped. There is no longer a hero cell to selectively favor and no line-clamp arithmetic to satisfy — this is a *stronger* floor than the retired hero-cell rule, not a weaker one: previously only the single 2×2 hero was guaranteed full prose, now every card is.
- **Serves:** Platform capability sections, Industries "applications" sections.
- **Reference implementation (rebuilt 2026-08-25):** `src/components/twin/AssetClassBento.tsx` — real, generic, sector-agnostic (`assets: SystemAsset[]` prop), not hardcoded to one page. Live on 3 real pages today: `/industries/water-wastewater`, `/industries/water-wastewater-1`, `/industries/water-wastewater-2` (a thin `SystemAssets.tsx` host on each). This is distinct from the 6 *other* industry pages (rail-transportation, defense-government, energy-utilities, hyperscale-data-centers, manufacturing-process) that reuse `AssetNode`'s glyph substrate through `TwinExplorer` for scenario diagrams — those consume the same glyphs, not this bento layout, which so far has only water-sector content. Rollout of the bento layout itself to the other 5 industry pages remains a real follow-up, not yet done — flag stale if this note still says that after they're built.

### 4. Facility Cross-Section Scroll
*(lineage: sticky-scroll narrative)*

The pinned visual is drawn as an **actual architectural cross-section**, not a generic product screenshot that happens to be sticky. The Seldon Engine's 7 layers stack as physical floors: Facility physics at the foundation, rising through Assets → Interoperation → Networks → Data fusion → Services, to Governance at the roofline. **Scrolling down = ascending from the physical plant toward oversight/reporting** (fix, flagged by independent Opus review — the original version said "scrolling down = descending," which directly contradicts its own foundation-to-roofline layer order; foundation is where the scroll starts, roofline is where it ends, so downward scroll necessarily moves upward through the stack) — this mirrors how OT engineers already think about the Purdue model's vertical stack, so the metaphor isn't decorative, it's load-bearing. The active layer fills solid cyan; inactive layers recede to a thin slate outline.

- **Motion:** this is the one pattern the Foundation Spec's 300-500ms diagram-timing tier exists for — every other pattern here uses the tighter 160-280ms UI band.
- **Accessibility:** a static jump-list of the 7 layer names exists below the visual for anyone who doesn't trigger scroll animation — **fix, flagged by independent review:** the jump-list must be explicitly stated as keyboard-navigable (not just a visual legend) with the active layer announced via an ARIA live region, or it's decorative, not operable. **Second fix, flagged by independent Fable review:** the live region needs `aria-live="polite"` plus announce-only-on-settle (~300ms after the active layer stabilizes) — without debouncing, a fast scroll crossing several layers fires a burst of announcements ("Networks… Data fusion… Services…") that turns the fix into screen-reader spam rather than useful state. Inactive-layer outlines also need a stated contrast floor (3:1, WCAG 1.4.11) — "thin slate outline" alone isn't a spec. `prefers-reduced-motion` swaps continuous transform for discrete layer-to-layer jumps.
- **Mobile (fix, flagged by independent review):** sticky-scroll has nowhere to live on a narrow viewport — a side-pinned cross-section pane doesn't fit. On mobile, this pattern is replaced entirely by a simple stacked list of the 7 layers (reuse Zone Sequencer's linear-sequence treatment), not a shrunk version of the desktop scroll effect.
- **Serves:** Seven-Layer Architecture Canvas (Foundation Deliverable 4).

### 5. Evidence Dossier Panel
*(lineage: tabbed/accordion panel)*

Tabs are styled as **document-control binder dividers** — restrained, technical, labeled with control codes ("EV-01 Provenance," "EV-02 Standards Trace"), not marketing labels like "Overview." Switching tabs is a **restrained crossfade, ~180ms, within the 160-280ms UI budget** (fix, flagged by independent review, then found incomplete by a second independent Fable pass: the original 200ms rotate-Y "page flip" had its *timing* justification fixed — "rounded up for a diagram-adjacent element" invented a motion category the spec doesn't recognize — but the 3D flip itself, a skeuomorphic staging effect, survived that fix untouched. Assurance's Composition Rule calls for a restrained, unstaged editorial register; a 3D page-turn is a performance, not a document. The flip is replaced entirely with a crossfade as the default transition, not merely retimed).

- **Restricted use, not a default:** this pattern is Assurance's alone. Composition Rules explicitly ban sales-style dashboard blocks there — Evidence Dossier's whole identity (a real document, not a dashboard) is exactly why it fits and nothing else on this list does.
- **Accessibility:** real ARIA tab/tabpanel roles with `aria-selected` state and roving `tabindex` (fix, flagged by independent review: originally unstated), arrow-key navigation between dividers, 44px minimum tap target on each tab, and the rotate-Y flip respects `prefers-reduced-motion` (fix, flagged by independent review: originally unstated).

### 6. Zone Sequencer
*(lineage: timeline / process stepper)*

Each step in Consulting's engagement model — or a deployment rollout sequence — carries its state on a **conventional numbered marker** (filled circle with the step number, standard progress-indicator language), sitting *inside* a **single ambient dashed zone-outline frame that wraps the whole sequence**, not one per step (fix, flagged by independent review, then found to be only a label change — not a mechanism change — by a second independent Fable pass: the original per-step "dashed perimeter fills solid on completion" mechanism still made every individual step visually "seal a security zone," regardless of whether the words "IEC 62443" appeared anywhere; a security-literate buyer reads that grammar as compliance evidence no matter what it's labeled. The fix now correctly separates the two jobs: the ambient outer frame is purely the family-recognition nod to Assurance's zone/conduit language — it never opens or closes — while the numbered markers, not any zone geometry, carry actual per-step completion state).

- **Guardrail carried:** Consulting's Composition Rule bans deep seven-layer architecture here — this stays a simple linear sequence, never a system diagram.
- **Accessibility:** a semantic ordered list backs the visual; sequence is never conveyed by position/color alone; each step's completion state ("Phase 2 of 4: complete") is announced as text, not just visual fill (fix, flagged by independent review: originally unstated).

### 7. Decision Ledger
*(lineage: comparison / decision matrix)*

Not a pricing grid. Modeled on an **actual engineering decision register**: it is a row-per-decision table (fix, flagged by independent Opus review — the original wording contradicted itself, describing "each row is one real decision" while also saying a CTA is "never repeated per NOW/NEXT/NEVER *column*," implying a three-column board that doesn't exist; there are no NOW/NEXT/NEVER columns, only a status chip per row). Each row is one real decision, carrying a rubber-stamp-style status chip — NEXT is a plain amber outline stamp (correctly "proposed/pending" per Foundation Spec), NEVER is a slate stamp with a strike-through — always paired with the word, never color alone. **("NEVER" reinstated 2026-08-24 — owner reversed the Foundation Spec's earlier public-label restriction; see `OXOT_Visual_Foundation_Spec.md` §Deliverable 2 Rules. This section briefly used "Deferred" instead, matching the old rule; that edit is reverted here.)**

- **NOW's token — RESOLVED 2026-08-24 (owner decision, see `OXOT_Visual_Foundation_Spec.md` §3.1):** flagged twice as open (first by independent review, then confirmed still-open by a second independent Fable pass) after an earlier fix gave NOW a solid amber stamp with an added urgency glyph — found insufficient, since amber's defined meaning is *proposed/pending* and NOW represents a *committed, active, urgent* decision; gluing a glyph onto the wrong-meaning token patches the symptom, not the mismatch. None of the Foundation Spec's 6 existing tokens cleanly meant "committed/active," so rather than inventing a 7th (barred by Visual_Rules' "no competing accent colors"), NOW now reuses `--signal-blue` — a genuine semantic fit, since blue's own definition already covers active routes/communications, and it was otherwise unused across the ledger's three states. NOW = solid blue stamp with the urgency glyph (now meaningful, since it sits on the right token); NEXT = amber outline stamp; NEVER = slate strike-through stamp (reinstated 2026-08-24, see note above). Clicking a row expands inline (reusing Evidence Dossier's tab styling) to reveal the Consequence Index value and its evidence citations. **Exactly one primary CTA for the whole ledger** ("Request the full decision register"), never one repeated per row or per NOW/NEXT/NEVER column.

- **Hard ban, not a suggestion:** no bare ✓/— checkmarks, no unlabeled red/amber/green light. That's precisely the generic pattern `OXOT_content-to-visual-mapping-table.md` exists to keep off this site — a real engineering register never renders state as an unlabeled dot.
- **Serves:** Four Decisions Switchboard (Foundation Deliverable 2). OXOT has no public pricing — this pattern serves the Decisions framework, full stop, never repurposed for a pricing page.

### 8. Case File Index
*(lineage: filterable card-grid)*

Each card is a **case-file folder tab** (visually continuous with Evidence Dossier's document-control language), with a classification-style header strip — turning a legal/claim-boundary requirement into an actual design element instead of buried fine print. Filter chips are visually styled as index tabs and use **`<button aria-pressed>` — committed as the one semantic, not offered as a choice between two** (fix, flagged by independent Opus review, then sharpened by a second independent Fable pass: tabs imply single-selection navigation, this is multi-select filtering, and `role="tablist"` would misrepresent it to assistive tech — but the original fix left `aria-pressed` and "a labeled checkbox-group" as two unpicked, actually-incompatible options, since `aria-pressed` must never appear on a checkbox role. `aria-pressed` buttons is the simpler, correctly-specified choice going forward). Filtering feels like paging through a physical case-file drawer.

- **Scope (fix, flagged by independent Fable review):** this pattern is specced for the **Case Studies index primarily** — its case-file metaphor, classification marking, and card schema genuinely fit engagement-style content. Reusing it verbatim for Resources (whitepapers/webinars) or Industries (sector overviews) was an unaddressed structural gap — a webinar isn't a case file and a sector overview carries no classification marking. If reused there, each index needs its own defined card-field variant, not the same schema stretched across three different content types.

- **Card classification is conditional, not fixed (fix, flagged by independent review — the single most serious finding across all 8 patterns; remedy corrected 2026-08-24, the original type-broke against `TwinScenario`'s own contract):** the original version printed "Illustrative scenario — no customer data" as a permanent template element on every card. Once real, published case studies enter this same index, that string becomes a false disclaimer printed on real customer work — a factual/legal accuracy risk, not a style nuance. The diagnosis was right; the first fix wasn't implementable — `TwinScenario.label` is a **required, single-literal-type** field per `OXOT_content-to-visual-mapping-table.md` (`label: "Illustrative scenario — no customer data"`), so "real case studies simply don't set it" is a type error, not an option. **Corrected fix:** the two record types never collide in the first place. Illustrative Twin scenarios are `TwinScenario` records and always carry that exact label, rendered by a `ClaimBoundaryNote`. Real case studies are `CaseStudyCard`/`CaseStudyMeta` records with their own `PublicationStatus` field — three states (Named / Anonymized / Illustrative), never a boolean — and render whichever of those applies ("Customer case study — published with permission" for Named/Anonymized, or no strip at all if the status doesn't call for one). No shared field, no possibility of the wrong string landing on real customer work.
- **Accessibility:** filter changes announce the new result count via an ARIA live region; every chip has a visible focus ring.
- **Serves:** Resources, Case Studies index, Industries index. Composition Rule for Resources: "do not use the Platform visual language everywhere" — Case File Index is deliberately its own visual identity, not Asset-Class Bento reused.

## Deployment & Case Study — the two patterns that don't reuse the list above

- **Air-Gapped Deployment Visual** (Foundation Deliverable 6): a custom-built trust-boundary diagram — a literal dashed security-zone perimeter (same shape language as Zone Sequencer) — showing the 3 real deployment modes (Island / one-way data diode / dedicated instance) as toggleable topology variants, not static cards. Stays custom per `OXOT_Component_Inventory.md`'s own decision that process diagrams aren't sourced from a library.
- **Case Study Editorial Template** (Foundation Deliverable 5): standard long-form Editorial typography (`DisplayHeading`/`SectionHeading`/`Lead`/`EvidenceCitation`) carrying the narrative, combined with Zone Sequencer for the engagement arc and Evidence Dossier styling for the trust-cascade layer (metrics, certifications). Not a new named pattern — long-form reading doesn't need one.

## How patterns combine

A page composes 2-4 of these, never all 8. A Platform-type page: Consequence Cascade Hero + Asset-Class Bento + Case File Index (related resources) — **fix, flagged by the page-alignment matrix (2026-08-24):** this example previously listed Evidence Dossier here too, contradicting pattern 5's own "Assurance's alone" restriction added during review. Evidence Dossier never appears on Platform. A Decisions page: a smaller hero + Decision Ledger + a plain accordion FAQ. A case study: the Editorial/Zone Sequencer/Evidence Dossier combination above.

## A motion-timing tension, resolved in OXOT's favor

External accordion UX research (Eleken) recommends ~300ms ease-in-out for expand/collapse. OXOT's own Foundation Spec caps UI interactions at 160-280ms, reserving 300-500ms for diagrams only. **OXOT's spec wins** — Evidence Dossier and Decision Ledger's row-expand both use the tighter band; only Facility Cross-Section Scroll (a genuine diagram) uses the slower tier.

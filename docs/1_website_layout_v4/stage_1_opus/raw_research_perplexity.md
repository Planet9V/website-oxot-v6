# Independent Research Pass — OXOT Component Inventory & Layout Patterns

## Part 0 — What the research changes about the spec (read first)

Six findings, each from research *plus* spec, not either alone.

**0.1 The spec's "SVG-first, WebGL optional" rule is market-correct, not a compromise.** The digital-twin market splits cleanly. CAD/simulation and reality-capture vendors (Siemens Simcenter, Ansys, Bentley iTwin, NVIDIA Omniverse, Hexagon HxDR) lead with 3D — but almost all as *static screenshots or looping video*, not interactive canvases. Process-industry and data-fusion vendors (AspenTech/Aspen Mtell, Emerson DeltaV Mimic, Cognite Data Fusion, much of AVEVA) **deliberately avoid 3D on public pages entirely**, leading with P&ID-style schematics and tag hierarchies because those match operator mental models. OXOT's buyers are the second group. §5's *"Use HTML/SVG/CSS first; do not make WebGL mandatory"* aligns with the segment OXOT sells into. Build schematic-first with conviction.

**0.2 Do NOT build the Twin Explorer or any diagram on shadcn/ui chart primitives.** A detailed 2024–25 accessibility review of shadcn/ui charts found: no text alternatives, arrow-key navigation that announces nothing, tooltips violating WCAG 1.4.13 (content on hover/focus must be hoverable and persistent), and docs claiming "Accessible" with no keyboard model described. §11 requires WCAG 2.2 AA and *"All diagrams have plain-language text equivalents"*; `OXOT_Mobile_Rules.md` says *"Never hide crucial state text behind hover."* Use shadcn/Radix for Tabs, RadioGroup, Dialog, Popover, Accordion, Toggle only. Every diagram is hand-authored SVG.

**0.3 There is a real W3C semantic vocabulary for exactly this diagram type.** The WAI-ARIA Graphics Module (`graphics-aria-1.0`) defines `graphics-document` ("structured graphics such as charts, maps, **diagrams, technical drawings, blueprints**") and `graphics-symbol` ("atomic, children presentational"). Maps 1:1 onto the OXOT contract: canvas = `role="graphics-document document"`; each `SystemAsset` = `role="graphics-symbol img"` with `aria-roledescription` carrying the `SystemAsset.type` enum and `aria-label` carrying `SystemAsset.label`. Fallback roles required (ARIA 1.0 ATs don't know graphics roles). **No competitor product researched does this** — a genuine differentiator for a company selling defensibility.

**0.4 The semantic palette is dark-mode-only and will fail light mode.** §11 mandates *"light mode is not an afterthought."* But §3.1 signals are tuned for `--ink-900`. Against `--paper-50 #F5F8F7`: `--signal-cyan #36D8D1` lands near 1.8:1 and `--signal-amber #FF9F43` near 2.2:1 — both fail the 3:1 non-text minimum (WCAG 1.4.11). Separately `--signal-slate #536761` on `--ink-900` is ~3:1 — fine as a stroke, fails as body text. **Fix:** each signal needs a per-surface pair (`--signal-cyan-on-dark` / `-on-light`); lightness must differ per theme while hue identity stays constant. That's the difference between "shares semantic tokens" and "shares hex values."

**0.5 Encode path state with stroke style, not colour — named precedent exists.** Dragos' NP-View integration ships **"dual-layer visibility"**: solid edges for *observed* traffic, distinct styling for *rule-permitted but unobserved* reachability. Microsoft Defender for IoT separately keeps **criticality** (star marker) orthogonal to **alert state** (red fill). OXOT has three orthogonal axes — `SystemPath.role`, `SystemPath.status`, `SystemAsset.criticality` — and only six colours. **Assign colour to `role`, stroke pattern to `status`, non-colour glyph to `criticality`.** Satisfies WCAG 1.4.1 for free; only way three axes fit legibly.

**0.6 FLAGGED — brand orange conflict.** Briefed `#E58B3F`; §3.1 specifies `--signal-amber: #FF9F43`. Different colours. If `#E58B3F` is the brand mark colour it needs a *separate* token (`--brand-orange`) reserved for identity — never the amber signal — because `OXOT_Visual_Rules.md` forbids *"multiple competing accent colors"* and §3.1 gives amber load-bearing meaning (proposed control / decision pending). **Conflating identity orange with decision amber breaks the semantic system. Needs a design-owner decision.**

## Part 1 — Component Inventory

### Tier 1 — Tokens & primitives
- `tokens.css` — §3.1 palette extended with per-theme signal pairs (0.4), spacing scale, `--focus-ring`, `--target-min: 44px`. Spacing/radii/breakpoints/focus rings undefined in spec but required by §11's WCAG 2.2 AA gate (2.4.11, 2.4.13) and Mobile_Rules' 44px.
- `<TypeRole>` — exactly five roles: display/section/lead/body/technical-label. §3.2 forbids ad hoc sizes; component makes it mechanically enforceable.
- `<Surface variant>` — canvas/technical/active-system/decision. §3.3 names exactly four; only `active-system` gets `--panel-blur` ("glass effects only for active technical system panels—not every card").
- `<MotionScope>` — duration bands ui (160-280ms)/explanatory (300-500ms), both → 0 under reduced motion. §3.4; JS path-tracing needs runtime `matchMedia` read so it snaps rather than animates.
- `<FocusRing>` — Tailwind ring + ring-offset, theme-matched offset colour (must be tokenised per theme or focus rings vanish on dark panels).

### Tier 2 — Diagram atoms (SVG layer; none wrap a charting library)
- `<SystemCanvas>` — root SVG, `role="graphics-document document"`, owns coordinate space + roving-tabindex ring. Finding 0.3.
- `<AssetNode>` — nine distinct glyphs switched on `SystemAsset.type` enum. A generic rounded rect + label is the "random node graph" the mapping table forbids.
- `<CriticalityMark>` — non-colour marker for context/important/critical. Precedent: Defender for IoT starred device, orthogonal to alert colour.
- `<PathEdge>` — colour from `role`, stroke pattern from `status`, arrowhead for direction. Finding 0.5.
- `<PathTrace>` — route animation in 300-500ms band; reduced motion → full route instantly with ordered-step overlay.
- `<ZoneBand>` — Purdue banding. Every OT product surveyed that shows Purdue uses horizontal bands, cross-band traffic only through named conduits (Defender for IoT renders by Purdue layer by default; Tenable exposes `purdueLevel: Level(1-5)`; Claroty and Armis band by level). **Never force-directed for the Purdue view** — destroys the property the view exists to show.
- `<ConduitGate>` — boundary crossing as a first-class object. Needed because `ProposedControl.type: "segmentation" | "brokered-access"` inserts *at* a boundary, not a node.
- `<ControlOverlay>` — amber insertion; reads `closesPathIds/preservesPathIds/residualPathIds`, restyles those three edge sets.
- `<ConsequenceChain>` — `operationalEffect → safetyOrReliabilityContext → businessImpact` ordered chain. Mapping table: process-chain diagram, avoid generic warning card.
- `<CanvasLegend>` — shows only encodings currently on screen — a three-axis encoding is unreadable without one.
- `<DiagramTextEquivalent>` — §11 requirement. §5's required-states table already dictates sentence templates ("A route exists from [entry] to [asset]") — template function over typed data, not hand-written copy per page.

### Tier 3 — State, evidence & decision
`<ViewSelector>` (five TwinView values as accessible tabs/radio, §6) · `<StateSummary>` (§5 states table supplies exact text) · `<EvidencePanel>` (resolves `Consequence.evidenceIds`) · `<EvidenceDrilldown>` (claim→artefact→source→date. Competitive note: of every product researched, only Bentley iTwin visually depicts provenance — change sets, model diffs, timelines. Cognite/AVEVA imply it via asset trees; everyone else treats lineage as narrative. Open ground for a company whose pitch is defensible evidence) · `<ControlOption>` · `<ResidualRecord>` (§7 requires residual exposure be shown — naming what the control does NOT close is the credibility mechanism) · `<ClaimBoundaryNote>` (mandatory `TwinScenario.label`, as a component so it can't be forgotten) · `<AuthorityNote>` (§7's "supports but does not replace engineering approval", required wherever a safety-function asset appears) · `<PriorityBoard>` (NOW/NEXT/deferred — mapping table explicitly says NOT to build the severity-score UI that Claroty, Tenable, Armis and Otorio all build; OXOT's differentiation is sequencing, not scoring) · `<RiskReductionCurve>` (no money values without approved inputs, §7).

### Tier 4 — Composition shells
`<ExplorerShell>` (reorders to the exact five-step mobile stack mandated by Mobile_Rules) · `<ComparisonLedger>` (three fixed columns per §7. Evidence: Baymard found 67% of participants used side-by-side spec comparison; AWS Cloudscape caps useful comparison at ~5 decision-relevant attributes — §7's table specifies 5/4/5, within budget, do not grow it) · `<SwitchboardShell>` · `<LayerRail>` (`?layer=L4` URL state, §8 requires it explicitly) · `<ObjectTraceShell>` · `<BoundaryDiagram>` · `<ProgressiveDetail>` (require a `reason` prop — §11 forbids hiding content "only to make a page shorter") · `<WideScrollRegion>` (Mobile_Rules permits horizontal scroll for exactly three cases, only with affordance AND summary).

### Tier 5 — Editorial, assurance & shell
`<CaseStudyFrame>` (§9 ten sections) · `<CaseStudyMeta>` (seven fields incl. Publication status, Last reviewed) · `<DecisionFlow>` (Decision → Constraint → Model → Options → Outcome, one component reused verbatim) · `<PublicationStatus>` (the one badge the system permits — constrains a claim rather than asserting trust) · `<ClauseTrace>` (clause-granularity — Dragos maps to named IEC 62443 SRs, Nozomi to parts 2-1/3-3, Claroty to 62443-3-3; general SaaS trust centres moved from badge walls to self-service report access) · `<SectorModel>` · `<DependencyGraph>` · Shell set (§13/§4: Platform/Consulting/Decisions/Industries/Assurance/Resources/Company + "Talk to an OT Engineer") · `<ScenarioProvider>` (typed context, deterministic reducer on view/scenario/proposedControl — §5's three keys — synced to searchParams via nuqs; on state change move focus to summary region + announce via live region).

**Deliberately excluded** (each present in competitors, each forbidden by OXOT spec): numeric asset risk score (Claroty/Armis/Otorio; PriorityBoard replaces it) · severity heat-map dashboard tile (Tenable) · customer-logo wall (§9) · ALE/percentage counter (§7) · generic equal-card grid (§11) · auto-rotating carousel (§2).

## Part 2 — Eight Named Layout Patterns

1. **Lens Bench** — Horizontal lens strip / canvas / state-and-evidence column. Spec: §5 explorer flow + seven-row required-states table; five TwinView enum values. Key insight: the same `assets` array renders five ways — a projection problem, not five diagrams. Each view needs a different layout algorithm (purdue = strict banding by zone; network = topology on SystemPath; process = material/energy order; attackPath = network + attackPathIds traced; consequence = collapse to chain). One force-directed layout serving all five loses meaning. Mobile → mandated five-step stack. Used on: Home, Platform, every Industry page.

2. **Three-Gate Ledger** — Three unequal columns: Baseline (widest, red) / Proposed control (amber) / Decision output (narrowest, densest), shared canvas above. Spec: §7's required-panels table dictates all three contents verbatim; semantic state rules dictate colour per column. Evidence: Baymard 67%; Cloudscape ≤5 attributes. **Scrubber deliberately rejected** — a drag-slider fails Mobile_Rules ("Every interactive state must be selectable without drag") and fundamentally: a wipe has two states, the model has three (closed/preserved/residual). The ledger can express residual; the scrubber can't.

3. **Question Switchboard** — Four questions as a vertical rail; one deep asymmetric panel. Spec: §6 in full, four fixed routes, six-step chain. Four equal cards violate both §6 ("a switchboard, not four equal static cards") and Visual_Rules ("More than three visually equal cards"). §6 naming constraint: not "NEVER" publicly — "Accept or defer" with review conditions stated.

4. **Depth Rail** — Seven layers vertical, L1 bottom → L7 top (physical below, governance above), four-part panel per layer, plus ObjectTrace mode. Spec: §8's layer table + four-step interaction + "Also provide Trace one object mode" + `?layer=L4`. Two modes answer opposite questions (what is a layer? / where does my pump live?) and §8 requires both. §8 rules out canvas-only graphics.

5. **Boundary Frame** — One fixed enclosure, three modes, only the arrows change (none/one inbound/defined integrations). Spec: §10's three-mode table. Arrow topology is the entire semantic payload. Mandatory-elements panel always visible — the passive-first claim ("no agents on PLCs, RTUs, or controllers") must not be mode-conditional. §10: defense examples notional/synthetic only.

6. **Evidence Spine** — Long-form single column, sticky left metadata spine, exactly one full-bleed artefact placed at the hinge — between §9 step 5 (pathway discovered) and step 6 (options tested), the moment the reader's model changes. Closes on the DecisionFlow graphic. Intentionally the least interactive pattern in the system — Composition_Rules: Resources should "not use the Platform visual language everywhere." Tonal shift is the point: proof reads as documentation, not product.

7. **Sector Cutaway** — Operational problem in the operator's own units first (never OXOT) → sector system model → one worked scenario reusing Lens Bench → sector CTA. No switchboard, no layer rail. Spec: Composition_Rules "Industry pages" verbatim. Mapping table spells out four distinct chains (Water: vendor→dosing PLC→disinfection; Rail: vendor→engineering workstation→interlocking; Hyperscale: BMS→cooling controller→capacity; Defense: support→facilities engineering→mission-support) and SystemAsset.type distribution differs per sector. If two industry pages look identical, the scenario data was not actually authored.

8. **Requirement Trace** — Framework selector + dense trace table (Requirement ID · Summary · What OXOT provides · Evidence artefact · Status), diagrams inline between clusters. No tiles, no scores, no gauges. Spec: Composition_Rules "Assurance pages" verbatim + §11. The row granularity IS the credibility — a "62443 compliant" badge is now a negative signal to this buyer. Status column must be honest: partial/not-covered rows make covered rows believable (same mechanic as ResidualRecord).

**Coverage:** Home → Lens Bench (+4 secondary) · Platform → Depth Rail (+4) · Decisions → Question Switchboard · Industries → Sector Cutaway · Assurance → Requirement Trace · Resources → Evidence Spine · Air-Gapped/Defense → Boundary Frame.

**Acknowledged gap: Consulting has no dedicated pattern.** Composition_Rules calls for an "engagement model and service detail… timeline or engagement journey" with "no deep seven-layer architecture" — a time-axis pattern none of the eight provides. Flagged rather than padded with a ninth ungrounded pattern.

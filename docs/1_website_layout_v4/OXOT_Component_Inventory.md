## When to reach for a tabbed layout (rule added 2026-08-25)

**A genuinely long enumerated list — many categories, each with several rows — is a real, positive reason to use `src/components/ui/tabs.tsx`.** Not a generic aesthetic preference for tabs: the trigger is content shape, judged case by case (roughly 6+ categories and 40+ total rows is the working threshold). Showing one category's rows at a time keeps the section from becoming mostly scroll. Full rule and the reference implementation (`TechnologyIndex.tsx`, `/industries/water-wastewater-2`, 8 categories/77 terms) are in `OXOT_Composition_Rules.md`'s Industry pages section — this entry exists so the rule is discoverable from the component side too, not just the composition side.

## Cross-document guardrails (added after swarm/direct review, 2026-08-24)

These are binding, not optional, per `OXOT_Composition_Rules.md`, `OXOT_Visual_Rules.md`, `OXOT_Mobile_Rules.md`, and `OXOT_content-to-visual-mapping-table.md`:

- **Section restrictions (Composition Rules):** no Tremor-style KPI-card dashboard components on **Assurance** ("no sales-style dashboard blocks"); no architecture-canvas/seven-layer-diagram components on **Consulting** ("no deep seven-layer architecture").
- **No hover-only interactions (Mobile Rules):** Skiper UI's hover-state techniques may only be used with a touch/tap equivalent. Never ship a hover-only-dependent interaction — this directly contradicts Mobile Rules if unguarded.
- **One focal element (Visual Rules):** carousels are not decorative filler — a carousel is a focal element in its own right. Never pair one with a competing CTA or headline in the same section.
- **No generic patterns reintroduced (content-to-visual-mapping-table):** do not use a plain checkmark list for Proposed Control content (use before/after route comparison instead), a generic shield/badge for safety linkage (use the hazard→barrier→consequence trace), or a generic ROI icon for investment decisions (use the risk-reduction curve) — even though generic B2B research (Perplexity) recommends these patterns broadly, OXOT's own mapping table explicitly bans them for these content types.
- **Real content only:** any testimonial/logo carousel or trust-badge strip must contain only real, approved OXOT content — never fabricated logos, metrics, or testimonials (Foundation Spec do-not list).
- **Retime everything (Foundation Spec motion rules):** no third-party component's shipped default animation timing is used as-is. Recharts, embla-carousel, Aceternity, MagicUI additions must all be retimed to 160–280ms for UI interactions and 300–500ms reserved for diagrams only, respecting `prefers-reduced-motion`.
- **WCAG 2.2 AA per component (non-negotiable acceptance criterion):** sortable tables need proper ARIA sort-state labels; carousels need keyboard navigation plus a pause control; sliders need ARIA range roles and keyboard step control. **Charts too** — this was omitted while `chart.tsx` was confined to a single deliverable, and it matters now that the Industries carve-out below opens it up. Verified 2026-08-24: `src/components/ui/chart.tsx` contains **no** `aria-*`, `role`, `<title>`, `<desc>`, or recharts `accessibilityLayer` anywhere in its 369 lines. As shipped it renders an unlabelled SVG that conveys its meaning through colour and shape alone — that is a 1.1.1 and 1.4.1 failure out of the box, not a polish item. The first Industries caller owns fixing it: an accessible name and description on the chart root, `accessibilityLayer` enabled for keyboard series traversal, series distinguished by more than hue, and the same figures reachable as text (the adjacent copy, a caption, or a small static table). A chart whose numbers exist only inside the SVG does not ship.
- **Map to a Foundation Deliverable, with an Industries carve-out (updated 2026-08-24 — see criticism #3, `OXOT_Composition_Rules.md`'s Industries floor rules):** charts/graphs primarily serve the **Investment decision** deliverable (risk-reduction curve, per `OXOT_content-to-visual-mapping-table.md`), not Baseline vs Virtual Control — §7's required panels there are baseline / proposed-control / decision-output, no chart. (Money-value display on the curve is an owner-confirmed exception to the Foundation Spec's general no-percentages/no-money-values rule.) **This is no longer `chart.tsx`'s only sanctioned use.** `chart.tsx` (recharts) is also a real, justified option on Industries pages, but only where the actual content is genuinely numeric/comparative — e.g. a sector's incident-frequency trend, an asset-criticality distribution, a before/after exposure-reduction comparison grounded in real `SystemAsset`/`TwinScenario` data — never as decoration standing in for a diagram, or in place of a single stat that would just be a number. `chart.tsx` currently has **zero real call sites anywhere in this repo** (re-verified 2026-08-24 two ways: no `src/` file imports `ui/chart`, and `recharts` appears in no `src/` file except `ui/chart.tsx` itself) — it isn't a proven pattern yet, so its first real use should be judged against this numeric/comparative bar, not treated as pre-approved by precedent.

  Three things make that bar checkable rather than assertable, because "genuinely numeric/comparative" is otherwise easy to claim about almost anything:

  1. **The numbers must already exist.** If the series has to be invented, estimated, or rounded into shape to make the chart read well, stop — that is the Foundation Spec's fabricated-metrics prohibition, and the **Real content only** guardrail above (written for testimonials and logo strips) applies with equal force to chart data. Name the source before drawing: real `SystemAsset`/`TwinScenario` fields, an owner-approved figure, or a cited external dataset. "Illustrative/representative figures" on a chart is fabrication with a disclaimer attached.
  2. **There must be enough real points that the shape carries the meaning.** A chart earns its place when position or ordering tells the reader something no sentence does. A two-point "trend" is a comparison; three flat categories is a table. If removing the axes would lose nothing, it wasn't a chart.
  3. **When it fails the bar, reach for the named alternative, not a text row.** The whole point of criticism #3 is that builders fell back to numbered text rows because nothing else was sanctioned. A single headline figure is `number-ticker.tsx` (already in `ui/`, already used). A short static series is the existing local kit `DataTable` described below. A relationship between assets is a custom SVG diagram, per the Process/system diagrams row above. Rejecting a chart is not a reason to reach for prose.

  One cost to accept knowingly: `chart.tsx` is pinned to recharts 2.x, flagged as upstream-deprecated tech debt in this file's own implementation-status table. The first Industries caller inherits that migration. That is a reason to be sure the chart is warranted — not a reason to avoid charting content that genuinely is numeric.

  `data-table.tsx` (the real `@tanstack/react-table`-based component at `src/components/ui/data-table.tsx`) primarily serves the Seven-Layer Architecture Canvas (evidence/BOM data) and Assurance evidence traces, and is equally available on Industries pages for genuinely tabular real data (e.g. a sector's asset inventory, a compliance-clause-to-evidence mapping) — not for content that's actually a list, or a diagram wearing a table's clothes.

But the first correction then mis-described the false positive, in a way that matters. A text search for `"DataTable"` returns **18** files, not 8, and they are not "a locally-defined helper per file." They are **four** separate kit-level `DataTable` definitions, imported by eleven callers:

  | `src/components/assurance/cyber-resilience-act/kit.tsx` | 7 |

All four are plain static `<table>` wrappers with no sort, filter, or tanstack behaviour, and their props have already converged on near-identical shapes (`head`, `rows`, optional `caption`, optional `minWidth`).

  That convergence is the actionable fact, and it sharpens the bar from "not for content that's actually a list" — which is a judgement call a builder can always win — to something checkable: **the static tabular need in this repo is already met four times over.** Reach for the real `ui/data-table.tsx` only when the reader has a genuine reason to reorder or filter — enough rows that scanning fails, and a column someone would actually sort by (criticality, layer, clause). If the table is short and read top-to-bottom, use the nearest existing kit helper instead; that is the cheaper, already-accessible, already-shipped path, not a fallback. Whoever does need sort/filter should expect to be `ui/data-table.tsx`'s first real caller — and should consider promoting one of the four static helpers rather than adding a fifth.

  The generated-imagery pipeline (`scripts/gimp-export.sh`, `scripts/blender-render-glb.py`, `scripts/openrouter-generate-image.sh` — all confirmed working) is a real, available Industries-page tool for hero backgrounds or facility/process photography where it adds real visual texture — matching the existing precedent on `/industries/rail-transportation`.

  Read that precedent carefully, because it is **two different justifications, not one**, and an earlier draft of this guidance collapsed them into a single sentence ("an image earns its place because it depicts something real and specific to the content beside it") that its own cited example does not satisfy. Both files were re-read in full on 2026-08-24:

  - **Compositional use — `RailHero.tsx`.** The image is `/images/cdt2/model-architecture.png`, and its docblock is explicit that it is a *generic* engine rendering reused from `/cdt-2`, "not a claim that this is rail-specific UI... an illustrative concept image, not a fabricated product screenshot." It is emphatically **not** specific to rail. What earns it its place is that it is real and already shipped, that it is honest about its own category, and that it is *composed* rather than boxed — bled past the container edge with a radial mask, holding the short side of an asymmetric `1.3fr / 1fr` hero grid. This is the sanctioned way to use a generic brand asset: as visual weight in a deliberate composition, never captioned or positioned so it reads as evidence of a specific claim.
  - **Depictive use — `RailDecisions.tsx`.** The image is `/images/cdt2/whatif-control-stack.png`, paired with decision 3 ("Can we change safely?") because it literally depicts a what-if control experiment against a baseline twin. Here specificity is the whole justification, and the docblock names it: "a content-driven asymmetry, not decoration."

  **The withholding test is what makes this a floor rather than a slogan.** Rail's depictive case is credible precisely because the other three decisions in the same `<ol>` get *no* image — no filler, no near-enough substitute — and render in a visibly different, plainer layout as a result. So: if a builder cannot point to a section on the page where they *declined* imagery because no fitting asset existed, the imagery on that page has not been reasoned about. A sparse-looking section is never itself the reason.

  Sequence still holds: reuse an existing shipped asset first (Rail does, for both images); generate new imagery via the scripts only when no existing asset fits the compositional or depictive role. And generation does not lower the bar — a newly generated image must clear the same two tests, and generating one is the point at which it is easiest to accidentally fabricate a "product screenshot."

  **THE REAL FAILURE MODE, CONFIRMED 2026-08-26: silently declining without ever reaching step 2.** A page build (Energy & Utilities, S07 Product Capabilities) shipped a "no imagery, declined" section, and the stated reason was that no existing asset in `public/images/` already depicted the content — step 1 of the sequence above failed, but step 2 (generate via the pipeline) was never even considered, and the section's own docblock called generating a stand-in "fabrication," conflating the Foundation Spec's ban on stock photography and false claims with a ban on the pipeline itself. "No existing asset fits" is the trigger for generation, not the reason to stop. `OXOT_Visual_Foundation_Spec.md`'s "Do not" list now carries a cross-reference back to this section for exactly this reason, and `OXOT_Agent_Build_Pipeline.md`'s Taskmaster prompt now requires an explicit reuse/generate/decline call with reasoning, rather than accepting a bare "no imagery."

  **Once an image has earned its place: a raster with a baked-in flat background needs its section's ground matched LITERALLY, not by token (technique, added 2026-08-26).** Where a PNG is not cropped with transparency but carries its own flat single-colour ground — the CDT-architecture renders are the live case, pure white in the light variant, pure black in the dark — the section containing it must paint that same literal colour (`bg-white dark:bg-black`), not the nearest theme token. `--card` in dark theme is `hsl(220 15% 6%)`, a very dark blue-grey rather than true black, so a token-coloured section leaves a faint but visible tonal seam at the image's edge. Light mode's `--card` happens to be pure white today, but that is a coincidence a future token change would silently break, so state both sides explicitly rather than leaning on the one that currently agrees. Two consequences to know before reaching for this: it **propagates inward** — any panel wrapper nested inside that section must also skip `bg-card`, or it reintroduces the same near-black-behind-pure-black seam the section background was changed to remove (a bordered panel can still be a border-only frame with the section's pure ground showing through it) — and it **travels with the figure**, so anywhere that figure is reused, the consuming section carries the same treatment. Cropping the asset with transparency is still the fix of first resort; this technique is for assets you do not control or cannot re-export. Reference implementation: `Capabilities.tsx` on `/industries/water-wastewater-3`, whose docblock states the reuse rule at the point of use.

  None of this loosens the underlying instinct — don't reach for `chart.tsx`, `data-table.tsx`, or the imagery pipeline without a specific, real reason tied to the actual content: real numbers whose shape carries meaning; a table someone would genuinely sort or filter; an asset that either depicts the adjacent content or does honest compositional work. It removes the blanket restriction that confined `chart.tsx` to a single deliverable and left Industries pages with no real component to reach for beyond text rows — a root cause behind criticism #3 (over-reliance on numbered text-row sections) in the 2026-08-24 test-page review. Carousels primarily serve the Case Study Editorial Template (related-study cards) — unchanged by this update.

  **Read this together with the Industries component-variety floor in `OXOT_Composition_Rules.md`, and note the two rules pull in opposite directions on purpose.** That floor requires a minimum number of structurally distinct non-text-row treatments per page; this section sets the quality bar each one has to clear, and explicitly binds `chart.tsx` to the numeric/comparative test above. A page that satisfies the variety floor by adding a chart with invented numbers, a sortable table nobody would sort, or a decorative render has not passed — it has swapped criticism #3 (monotony) for the Foundation Spec's fabrication prohibition, which is the worse failure. If a page genuinely cannot reach the variety floor without breaking one of these bars, that is a signal the *content* is thin, and the fix is content, not components. Say so rather than padding.

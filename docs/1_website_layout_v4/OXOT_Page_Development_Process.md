# OXOT Page Development & Enhancement Process

**New to this system? Start with [`OXOT_README.md`](./OXOT_README.md) first.**

**Status: durable reference. Consult this file before building or enhancing any page — do not improvise the process.** See [`OXOT_Master_Record.md`](./OXOT_Master_Record.md) for the full index of this system, including the 8 layout patterns, component inventory status, and review history.

This document operationalizes `OXOT_Visual_Foundation_Spec.md`, `OXOT_Visual_Rules.md`, `OXOT_Composition_Rules.md`, `OXOT_Mobile_Rules.md`, `OXOT_Visual QA Checklist.md`, `OXOT_content-to-visual-mapping-table.md`, and `ruflo_workflow_mandate.md` into one repeatable loop. It does not replace those files — it tells you the order to apply them in.

## Where we are in the Foundation Spec's own sequence

The Foundation Spec (Section 11) defines a 7-phase build order: (1) design tokens/shell, (2) Home Hero + Twin Explorer, (3) Four Decisions + Virtual Control, (4) Seven-Layer Canvas, (5) Case Study Template, (6) Air-Gapped Deployment Visual, **(7) full sitemap rollout — "composed from approved patterns."** Home and CDT-2/Twin (protected pages) cover phases 1–2. **Every page touched under this process is Phase 7 work** — its own instruction is explicit: *"The site must look designed around evidence, systems, dependencies, and decisions — not around a template library."* Never reuse one page's layout for another just because it's convenient.

## Per-page process

1. **Recall** — `memory_search` the Ruflo `decision-log` namespace for this page/section before any decision. Check for prior work, prior mistakes, established patterns.
2. **Reference check** — identify which Foundation Deliverable pattern this page composes from, which `OXOT_Composition_Rules.md` section applies (Home / Platform / Consulting / Industry / Assurance / Resources — each has different, non-interchangeable rules), and which 2-4 patterns from `OXOT_Layout_Styles.md` compose the page visually. **Treat the named patterns as a starting scaffold, not the full inventory** — a real page (Industries pages are the proof case) will need bespoke, sector/page-specific components layered on top to earn its own visual identity, per the Phase-7 instruction below ("designed around evidence... not around a template library"). Budget for that in scope, don't expect "2-4 patterns" to fully describe the finished page.
3. **Audit against rules** — check the page (existing or planned) against `OXOT_Visual_Rules.md`: one focal element, ≤1 primary CTA, ≤3 equal-weight cards, no competing accents, and the specific composition rule for that section.
4. **Mobile pass** — check against `OXOT_Mobile_Rules.md`: stacking order (View selector → Canvas → State summary → Evidence drawer → CTA) for complex system visuals, 44px touch targets, no hover/drag-only interactions.
5. **Build/enhance** — implement only what's flagged, using the approved component family (Shell / Editorial / Decision / Twin / Proof / Deployment — Foundation Spec Section 13) and the content-to-visual mapping table's "use this, avoid that" per content type.

   **Closing-CTA check, before leaving this step (added 2026-08-26).** The site's generic "Talk to OXOT" `ContactBand` renders unconditionally for every route from `[locale]/layout.tsx`. If the page you just built carries its own page-local closing CTA, add its locale-free route to the exported `SUPPRESS_CONTACT_BAND` Set in `src/components/shell/nav.ts` — otherwise the generic band renders a second, redundant CTA directly beneath the custom one. It is a suppression list, not an opt-in registry: a route added there is trusted to render its own equivalent CTA and nothing renders one for it, so only add a route that genuinely has one. Real miss: `/industries/water-wastewater-2` and `-3` were both built with a real page-local `IntakeCta` closing section and neither was added, duplicating the closing CTA on both until a later audit caught it (fixed 2026-08-25). A one-line step that is silently skippable on a fresh build is exactly the kind that belongs on this list rather than in a component's own comment.
6. **QA gate — enforced, not ad hoc (owner directive, 2026-08-24).** "I checked it" does not satisfy this step. Write out `OXOT_Visual QA Checklist.md`'s 5 categories — Hierarchy, Brand, Density, Interaction, Consistency — **one line each, pass or fail, with a one-sentence reason**, and include that written checklist in the Persist step's `memory_store` payload (step 7). This became a hard rule after a real failure: an earlier page build named the correct pattern in its own Reference-check step (step 2), then the Build step (step 5) silently abandoned it and substituted an unrelated technique instead, and the QA gate — done informally, not written out — caught none of it. Written output is what makes the gate checkable after the fact, by the owner or a future session, instead of trusting a summary. **A fail routes back to step 5. Never ship with a caveat.**

   **Run `scripts/measure.mjs` — mandatory on every page, not only Industries pages (added 2026-08-26).** The written checklist does not replace the automated harness, and the harness does not replace the checklist; both are required, and the harness runs first so the checklist is written against measured facts. Invocation is as set out in the Industries block below (locale-prefixed, **both locales**, explicitly passed). One run returns one verdict and one exit code across every gate it carries — h1 count, text contrast and 1.4.11 non-text contrast in both themes, ghosted text, dead internal links, console errors, document overflow, sibling balance, and orphaned narrow text. Any non-zero count is a fail that routes back to step 5. Two of those gates are recent and easy to miss:

   - **`narrow-text=N` — orphaned narrow text (`collectNarrowText`, added 2026-08-25).** Flags every `<p>`/`<h2>`/`<h3>` of 15+ characters inside a `main section[id]`/`div[id]` whose rendered width is under **75%** of its section's — i.e. a reading-width cap (`.prose-measure`, a hardcoded `max-w-*`) left on a standalone full-width block, leaving dead space beside it. Three exemptions, all mechanical: the block sits inside a real multi-column context (a computed `grid-template-columns` with 2+ tracks, or a flex row with 2+ children each rendering wider than 40px); it carries the `data-narrow-ok` opt-out; or its own computed `display` starts with `inline` (pills and badges size to their content by design and are exempt outright). **Opt-out, not opt-in, deliberately** — unlike a balance group, whether a block sits in a real column is checkable from the DOM, so this runs over every text block by default and a genuine editorial choice (a deliberately narrow pull-quote) declares itself with `data-narrow-ok`. This check exists because the written floor rule alone did not hold: the same defect was independently reintroduced by different builders on two separately-built pages on the same day, on the same section types, after being fixed manually once already. Treat a `data-narrow-ok` you are tempted to add as a finding to justify in the checklist, not a way to clear the gate.
   - **Eight overflow viewports, not four (widened 2026-08-25).** `VIEWPORTS` is now `390 / 834 / 1024 / 1152 / 1280 / 1440 / 1536 / 2560`. The four added widths are Tailwind's own `lg` / `lg+128` / `xl` / `2xl` breakpoints — the widths a Tailwind-authored header or grid is most likely to break at or just past. Added after a real incident: `site-header.tsx`'s desktop nav switched on at its own `lg:` breakpoint before it had room and overflowed the whole document by 232px at 1024px and 104px at 1152px, entirely invisible to the old 4-width set (which left a 606px unmonitored gap between 834 and 1440) and caught only by the owner's own screenshot. Do not narrow this list back down for speed.

   **Industries pages: measurable sibling-balance check (owner directive, 2026-08-24, following the `/industries/water-wastewater-1` 5/10 review — ties to the sibling-content-balance and pane-balance floor rules in `OXOT_Composition_Rules.md` and `OXOT_Layout_Styles.md` Patterns 1–3. Mechanism rewritten the same day by an independent Opus second pass that read `measure.mjs` and the live components: the first draft's threshold, section list and invocation were each wrong in a way that would have failed correct code and passed the actual defect.)** A written "looks balanced" line does not satisfy this step — it must be measured, and measured against the number the governing rule actually states.

   - **Extend `measure.mjs`; do not fork it.** `scripts/measure.mjs` (real repo: `.worktrees/chore-local-dev-postgres/scripts/measure.mjs` — read, confirmed working) already launches Playwright, forces each theme by cookie and asserts it took, scrolls the whole page so every in-view reveal has fired, and reads real geometry with `getBoundingClientRect()` — in the ask-size count, the ghosted-text filter and the 1.4.11 graphics pass. (It does **not** use that primitive for overflow detection; overflow is `documentElement.scrollWidth > clientWidth + 1`. The first draft of this paragraph cited overflow as the precedent and was simply wrong about the file.) Add balance to `collect()`'s returned object, to the `fail` expression and to the console line, so one gate still returns one verdict and one exit code. A second script drifts out of sync with the first defect that gets fixed in only one of them.
   - **Invocation — locale-prefixed, both locales, explicitly passed.** Every route lives under `src/app/[locale]/`, there is no `middleware.ts`, and the locale layout calls `notFound()` on an unrecognised locale — so an unprefixed path 404s and the harness throws by design (*"refusing to grade a page that did not render"*). Its built-in default `ROUTES` list is unprefixed and predates this app, so running it bare fails on the first route and never reaches your page. Run it as `MEASURE_BASE=http://localhost:3100 node scripts/measure.mjs /en/industries/<slug> /nl/industries/<slug>`. **Both locales are mandatory here, not diligence for its own sake:** this rule exists because copy height drives pane height, the real components render bilingual copy through `pick(..., locale)`, and Dutch runs longer than English. The harness's own history is the argument — 11 of 11 Dutch pages scrolled sideways at 834px while 0 of 11 English pages did, because nobody had looked at the other locale.
   - **Threshold — take it from the rule governing that group, not one flat number.** Pattern 1's two hero panes cap at 1.5x, so the shorter pane must be **≥ 67%** of the taller. Every other marked group falls under `OXOT_Composition_Rules.md`'s site-wide 2x floor: **≥ 50%** of the tallest sibling. A flat "~50%" gate would pass a hero row at 55% that Pattern 1 explicitly fails — the gate must never be looser than the rule it enforces — and "roughly" is not a comparison a machine can make, so write the exact number per group. A group outside its ratio is a fail *unless* the section carries the stated, content-based reason `OXOT_Composition_Rules.md` permits; record that reason alongside the ratio, never instead of it.
   - **Measure both of the floor rule's measures, not just height.** The Composition rule is written on rendered height **and** count of distinct content elements, worse governs — so capture both per sibling. Height alone is insufficient and would have missed the review's flagship finding: in a CSS grid a cell's height comes from the rows it spans, not from its own content, so the label-only 2×2 bento hero measured *tallest in its group* while rendering almost nothing.
   - **The Asset-Class Bento is not a height-ratio group.** Rebuilt 2026-08-25 from criticality-sized grid cells (2×2 hero / 2×1 / 1×1) to 3 horizontal tiered bands (Critical / Important / Context, see `OXOT_Layout_Styles.md` Pattern 3) — every card is uniform size *within* a band, so there is no cross-tier height ratio to measure, and naming the bento's bands as a sibling-height group would just compare bands of different population sizes (a 1-card band against an 8-card band), which this rule was never built to answer. `measure.mjs`'s own header states the doctrine twice, from two different real incidents: *a gate that invents failures gets ignored, which is worse than having no gate at all.* Check the bento on **content** instead: every card's description must render in full, unclamped — Pattern 3's content floor now applies uniformly to every card, not just a single hero cell.
   - **Mark the groups; report the count of marks.** Do not sweep every grid child on the page: nav lists, footer columns, badge rows and icon strips are unbalanced by design and would bury the real findings under noise. Follow the harness's existing opt-in idiom — a container declares itself with `data-balance-group="<name>"` exactly as a meaning-bearing figure declares `data-gfx-meaning`, and the **count of marked groups is printed per route**, so an unmarked multi-part section surfaces as missing coverage rather than as silent success. On an Industries page, mark at minimum the Consequence Cascade Hero's two panes and the Three-Gate Ledger's three columns.
   - **Capture conditions.** Default, pre-interaction state — no selection, no expansion, no hover — or progressive disclosure walks straight through the rule. Desktop only, at 1440×900 and 2560×1440: below `lg` these panes stack and are no longer siblings in a row, and Pattern 1's ratio is explicitly desktop-scoped. Keep the wide viewport, because a max-width copy pane beside an aspect-locked diagram gets *relatively* shorter as the viewport grows. Capture after the harness's existing scroll pass and settle, never at first paint — `BlurFade` cells start at opacity 0 under a transform, and `getBoundingClientRect()` returns the transformed box. One theme is enough; nothing here is colour-dependent. Skip any group with fewer than two visible children, and exclude children that are `display:none` at that breakpoint or absolutely positioned, or a 0-height decorative node will auto-fail its own group.
   - **Record the measured ratios — both measures, per group, per locale** — in the written checklist this step already requires, and bind them to the same harness run and commit as the attached screenshot. A fail here routes back to step 5 exactly like a checklist fail.
7. **Persist** — `memory_store` to `decision-log`: what changed, why, any new pattern this establishes for future pages, **and the written 5-category QA checklist from step 6.**

## Reusable technique — building a real, interactive worked-scenario diagram (`*ScenarioDiagram.tsx`)

Proven across all 6 Industries pages (2026-08-24). Use this whenever a page's Foundation-Spec deliverable calls for a "worked scenario" or "modelled chain/cascade" and the page's design does not already have a deliberate, reasoned static-only implementation (check first — `/decisions/change-safely` and `/decisions/investment` are intentionally static server-rendered SVG, not gaps to fill).

1. **Survey the page's own real content first.** Read the page's `content.ts` in full (dispatch a parallel Explore agent per page if doing several at once) — specifically the worked-example/chain array. Never fabricate scenario data.
2. **Classify each chain step** as ASSET (a `SystemAsset`, one of the 9 types in `src/components/twin/types.ts`) vs CONSEQUENCE/EFFECT text. Flag genuine ambiguity rather than guessing. Source data will not always cleanly support a uniform node count across pages — that's fine; use exactly as many real assets as the content supports (seen as few as 3, as many as 4 across the 6 pages built so far), and note the reasoning in a comment.
3. **Encode paths correctly**: `SystemPath.status` (open/controlled/closed/unknown) drives color; `SystemPath.role` (required-flow/attack-path/management/vendor-access) drives `strokeDasharray`. Never conflate the two.
4. **Build `<Sector>ScenarioDiagram.tsx`** in that page's component folder: `SystemAsset[]`/`SystemPath[]` consts + a `TwinExplorer` render, wrapped in that page's own visual chrome (don't impose a generic wrapper — match the page's established identity, e.g. sharp corners for Defense, rounded for Water).
5. **Wire it into the real `*WorkedExample.tsx`**, removing any now-dead plain-text chain renderer it replaces (grep for other usages before deleting a shared helper).
6. **Verify live, not self-reported**: `tsc --noEmit`, render in a real browser (screenshot), functional keyboard-interaction check (`document.activeElement`, not just visual), console-clean.

Reference implementation: `src/components/industries/rail-transportation/RailScenarioDiagram.tsx` (first built, most heavily commented). Full component substrate spec: `docs/OXOT-DIAGRAMMING-SPEC.md` (real repo).

## Reusable technique — a real Asset-Class Bento (Pattern 3), not a re-skin

Built 2026-08-24 after a real process failure: an earlier build named "Pattern 3 (Asset-Class Bento)" correctly in its own Reference-check step, then substituted an unrelated technique during the Build step without ever re-checking `OXOT_Layout_Styles.md`'s actual pattern text. Use this to avoid repeating that.

1. **Re-read the pattern's real definition before building anything** — don't build from memory or from what a sibling page happens to do. `OXOT_Layout_Styles.md` §3's actual requirement (rebuilt 2026-08-25): cells are the 9 real `SystemAsset.type` values, grouped into 3 horizontal tiered bands by `criticality` (Critical / Important / Context), every card uniform size within its band, tier carried by band position + label + rail-intensity — never by cell area or span. Single-color line-drawn glyphs, focus order matching visual/DOM order (WCAG 2.4.3, unchanged by the rebuild).
2. **Check whether the target section's content is actually asset-shaped** before forcing the pattern onto it. A list of abstract product capabilities is not a `SystemAsset[]` — if a page's "applications section" content doesn't fit, that's a real finding to surface, not something to silently work around by building a different, easier component instead.
3. **Derive real per-asset data from the page's own existing content** if no `SystemAsset[]` already exists for the section — Architecture tables, Hero control lists, and any already-typed assets in that page's `*ScenarioDiagram.tsx` are real sources; cite where each asset came from. Never fabricate an asset to fill out the 9 types.
4. **Reuse the shared `AssetClassBento`** (`src/components/twin/AssetClassBento.tsx`, generic `assets`/`title`/`intro`/`locale` props) rather than rebuilding the grid logic per page.

Reference implementation: `src/components/industries/water-wastewater/WaterSystemAssets.tsx` (thin host) + `src/components/twin/AssetClassBento.tsx` (shared logic, rebuilt 2026-08-25 to tiered bands — see above). Live on all 3 water-sector pages (`water-wastewater`, `-1`, `-2`, the latter two hosted by their own `SystemAssets.tsx`) as of 2026-08-25. Not yet rolled out to the other 5 non-water industry pages — a real follow-up, not assumed done.

IEC 62278-1:2025 and IEC 62278-2:2025 do not change the purpose of RAMS—specifying and demonstrating reliable, available, maintainable, and safe railway systems—but they make the modeling approach more explicit, **system-of-systems oriented, lifecycle-integrated, and safety-method driven**. Together, they cancel and replace IEC 62278:2002. [webstore.iec](https://webstore.iec.ch/en/publication/68933)

For the OXOT Cyber Digital Twin, this is a strong fit: the Twin should become the structured model behind the multi-level system definition, interfaces, risk-reduction strategy, safety requirements, safety case, configuration changes, and evidence traceability.

## What changed

| Earlier IEC 62278:2002 approach | IEC 62278-1/-2:2025 emphasis | Modeling implication |
|---|---|---|
| One combined RAMS document | Split into **Part 1: Generic RAMS Process** and **Part 2: Systems Approach to Safety** | Separate the broad lifecycle/RAMS model from detailed safety/hazard/requirement models, while keeping them linked |
| Broad railway system lifecycle | Explicit **multi-level system approach** and railway-system overview | Model hierarchy must be traversable: national network → line/corridor → subsystem → equipment → component/configuration item |
| Lifecycle process defined at a high level | Updated correlation between RAMS management and system lifecycle | Every model object needs lifecycle state: concept, design, implementation, validation, operation, modification, withdrawal |
| Safety methods embedded in the old combined standard | Part 2 provides dedicated safety-related guidance and methods | Create explicit hazard, safety requirement, safety integrity, barrier, evidence, and acceptance relationships |
| Risk reduction discussed in context | Explicit risk-reduction strategy added in Part 1 | Model risk controls as decisions with treatment type, owner, effectiveness, residual risk, dependency, and review trigger |
| Project scale handled more implicitly | Explicit tailoring to project scope and size | Support “small modification” and “network-wide modernization” templates without weakening traceability |
| Independent assessment and safety-case evidence less prominent in the generic model | Part 1 explicitly adds organizational requirements, independent safety assessment, and safety case | Model assurance roles, independence, approvals, evidence status, open issues, and safety-case claims |

IEC 62278-1:2025 specifically adds multi-level system approach, railway-system overview, risk-reduction strategy, organizational requirements, project tailoring, independent safety assessment, a dedicated safety-case clause, and system-definition guidance. [standards.iteh](https://standards.iteh.ai/catalog/standards/iec/3b644430-cd5e-4291-bfc4-b700f7b45c5b/iec-62278-1-2025)

## The main modeling shift

### From asset inventory to multi-level railway system model

The biggest change for your Cyber Digital Twin is that the model should not stop at devices and network zones. It needs to represent the railway at multiple levels, with explicit containment and dependency relationships.

```text
Railway system
├─ Network / national operating capability
│  ├─ Corridor / route / territory
│  │  ├─ Line section / signaling area / control zone
│  │  │  ├─ Subsystem
│  │  │  │  ├─ Interlocking
│  │  │  │  ├─ CBTC zone controller
│  │  │  │  ├─ ETCS / PTC support service
│  │  │  │  ├─ Traction-power SCADA environment
│  │  │  │  └─ Depot / station / tunnel OT
│  │  │  └─ Interface
│  │  │     ├─ Train-ground radio
│  │  │     ├─ Control center connection
│  │  │     ├─ Field communications
│  │  │     └─ Vendor maintenance route
│  │  └─ Operational capability
│  │     ├─ Safe train movement
│  │     ├─ Route setting
│  │     ├─ Headway / capacity
│  │     ├─ Passenger information
│  │     └─ Freight throughput
│  └─ Supporting dependencies
│     ├─ Telecoms
│     ├─ Power
│     ├─ Time synchronization
│     ├─ Identity / certificates
│     ├─ Supplier support
│     └─ Spares and maintenance teams
```

Each object should be navigable in both directions:

```text
Asset → subsystem → railway function → service consequence

or

Operational capability → required functions → systems → components
```

That supports the new multi-level system approach and allows the Twin to answer: **“What must remain available to keep this railway capability operating safely?”** [standards.iteh](https://standards.iteh.ai/catalog/standards/iec/3b644430-cd5e-4291-bfc4-b700f7b45c5b/iec-62278-1-2025)

## Part 1: generic RAMS process

### What the Twin should add

IEC 62278-1 is the governing lifecycle and RAMS-management layer. The Twin should model **who owns the requirement, where the evidence lives, how it changes, and what lifecycle state applies.**

### 1. Lifecycle state

Every important object should carry a lifecycle context:

| Model object | Useful lifecycle states |
|---|---|
| Railway system / subsystem | Concept, system definition, design, integration, validation, acceptance, operation, modification, withdrawal |
| Asset / configuration item | Planned, installed, commissioned, operational, degraded, maintenance, retired |
| Requirement | Draft, approved, allocated, verified, validated, superseded |
| Hazard / risk | Identified, analyzed, treated, accepted, monitored, closed, reopened |
| Control | Proposed, modeled, approved, implemented, tested, operational, withdrawn |
| Evidence artifact | Draft, reviewed, approved, expired, superseded |
| Supplier / component | Qualified, active, constrained, end-of-life, substituted, withdrawn |

This makes RAMS a continuous lifecycle model, not a static safety dossier created at the end of a project.

### 2. Requirement traceability

The Twin should connect:

```text
Operational need
        ↓
RAMS requirement
        ↓
System / subsystem allocation
        ↓
Technical requirement
        ↓
Design object or control
        ↓
Verification evidence
        ↓
Validation / acceptance evidence
        ↓
Safety-case claim
```

For example:

```text
Operational need:
Maintain safe train movement through a terminal junction.

        ↓

Availability requirement:
Interlocking service availability must support planned headway.

        ↓

Allocated systems:
Interlocking + field power + train detection + OCC communications.

        ↓

Cybersecurity requirement:
Remote engineering access must not create a persistent route into
the live interlocking zone.

        ↓

Control:
Brokered vendor access + segmentation + MFA + session recording.

        ↓

Evidence:
Topology analysis + firewall simulation + access test +
maintenance procedure + planned possession validation.
```

### 3. Risk-reduction strategy

The 2025 Part 1 explicitly introduces a risk-reduction strategy. In the Twin, this should be more than a risk register field.

```text
Hazard / cyber scenario
        ↓
Risk source and causal pathway
        ↓
Safety and service consequence
        ↓
Candidate risk-reduction measures
        ↓
Effectiveness, feasibility, cost, operational constraint
        ↓
Residual risk and acceptance decision
        ↓
Verification, validation, monitoring, and review
```

This fits OXOT’s existing **NOW / NEXT / NEVER** model very well:

| OXOT outcome | IEC 62278 interpretation |
|---|---|
| **NOW** | Risk requires immediate treatment because the pathway is credible and the operational/safety consequence is not tolerable |
| **NEXT** | Treatment is justified but should be sequenced into a planned project, possession, modernization, or maintenance window |
| **NEVER / accepted** | The route is unreachable, consequence is limited, or risk is tolerable with documented compensating controls and review triggers |

The key adjustment: in railway RAMS language, “NEVER” should not be presented as permanent dismissal. Use **“Accepted / deferred under controlled conditions”** with an owner, evidence, review trigger, expiry, and change condition.

### 4. Organization and independence

The new Part 1 makes organizational requirements and independent safety assessment more visible. Your model should therefore represent not only technical facts, but accountable parties.

```text
Requirement
├─ Owner
├─ Approver
├─ Safety authority
├─ Security authority
├─ System integrator
├─ Independent assessor
├─ Evidence reviewer
├─ Acceptance status
└─ Review / expiry date
```

This matters for OXOT because a technically correct model does not become assurance evidence until the right party reviews and accepts it.

## Part 2: systems approach to safety

### What the Twin should add

IEC 62278-2 provides the dedicated safety-related methods that support the Part 1 safety-management process. It emphasizes a technology-neutral systems approach: define the system, understand hazards, derive safety requirements, allocate them to subsystems, determine safety integrity needs, demonstrate evidence, and support safety acceptance. [webstore.iec](https://webstore.iec.ch/en/publication/79793)

### 1. Explicit hazard model

Your model should introduce a first-class **Hazard** object.

```text
Hazard
├─ Hazard ID
├─ Description
├─ Railway operational context
├─ Initiating event
├─ Causal factors
├─ Affected system / subsystem
├─ Safety consequence
├─ Severity
├─ Frequency / exposure assumptions
├─ Existing barriers
├─ Safety requirements
├─ Cybersecurity assumptions
├─ Residual risk
├─ Owner
└─ Evidence links
```

Example:

```text
Hazard:
Unauthorized or incorrect route-setting behavior at a terminal junction.

Initiating cyber event:
Compromised engineering workstation reaches interlocking configuration path.

Railway consequence:
Potential unsafe condition prevented by fail-safe behavior, but high-capacity
terminal becomes unavailable or restricted.

Safety barriers:
Interlocking logic, change authorization, configuration validation,
segmentation, controlled maintenance access.

Cybersecurity requirements:
No persistent vendor route to configuration environment; controlled access;
integrity verification; auditability; validated update process.
```

### 2. Safety requirement allocation

Part 2 emphasizes deriving safety requirements and allocating them to the right subsystem. The Twin should trace that allocation:

```text
Hazard
        ↓
System-level safety requirement
        ↓
Allocated subsystem requirements
        ↓
Technical / operational / cyber controls
        ↓
Verification and validation evidence
```

For a cyber-relevant railway example:

```text
System safety requirement:
Prevent unauthorized alteration of interlocking configuration.

        ↓

Allocated requirements:
- Engineering workstation must enforce named-user access.
- Remote support must be brokered and time-limited.
- Interlocking network must be segregated.
- Configuration packages must be integrity-protected.
- Change workflow must require approval and evidence retention.

        ↓

Evidence:
Access design, firewall model, configuration signing evidence,
procedure, test result, independent review.
```

### 3. Safety integrity context

The Twin should not calculate or assign SIL automatically. But it can model the **relationship** between:

- Safety-related function.
- Hazard and tolerable-risk target.
- Allocated requirement.
- Safety integrity requirement.
- System/subsystem/component carrying the requirement.
- Verification/validation evidence.
- Cyber assumptions on which the safety claim depends.

```text
Safety function
        ↓
Safety integrity requirement
        ↓
Allocated subsystem / component
        ↓
Cyber assumptions
Access control • configuration integrity • trusted communication
update control • segregation • maintenance procedure
        ↓
Evidence and acceptance
```

This exposes a critical question that often gets missed:

> **Which cybersecurity failure can invalidate an assumption underneath the safety-integrity claim?**

## Cybersecurity implications

IEC 62278-1/-2 strengthens the case for treating cybersecurity as a modelled cause of RAMS change—not a parallel compliance workstream.

```text
Cyber event
        ↓
Asset or interface compromised
        ↓
Failure mode introduced or altered
        ↓
Safety barrier, availability mechanism, or maintenance process affected
        ↓
RAMS consequence
        ↓
Risk-reduction and evidence update
```

This means your Cyber Digital Twin should model cyber events as:

- New initiating events in hazard analysis.
- Causes that can defeat, bypass, delay, corrupt, or disable safety barriers.
- Changes to reliability or availability assumptions.
- Constraints on maintainability and recovery.
- Inputs to system-change impact analysis.
- Triggers for reassessment when topology, firmware, remote access, supplier, or threat conditions change.

Europe’s Rail work explicitly identifies cybersecurity-related evolution as relevant to management of safety-related control-command and signaling-system changes. [rail-research.europa](https://rail-research.europa.eu/wp-content/uploads/2025/12/Annex_GB-Decision_09-25_WP2026.pdf)

## What changes in OXOT’s data model

The practical change is to add a **RAMS assurance layer** above the asset, network, and consequence model.

```text
Layer 1: Physical and operational system
Assets • functions • locations • processes • railway operations

Layer 2: Interfaces and dependencies
Communications • power • time • suppliers • personnel • maintenance

Layer 3: Cybersecurity model
Zones • conduits • identities • vulnerabilities • pathways • controls

Layer 4: RAMS model
Requirements • hazards • failure modes • barriers • degraded modes
reliability • availability • maintainability • safety integrity allocation

Layer 5: Assurance and governance
Evidence • verification • validation • independent assessment
safety-case claims • approvals • residual-risk acceptance • change history
```

### Recommended graph relationships

```text
(:OperationalCapability)-[:REQUIRES]->(:SystemFunction)
(:SystemFunction)-[:IMPLEMENTED_BY]->(:Subsystem)
(:Subsystem)-[:CONTAINS]->(:Asset)
(:Asset)-[:DEPENDS_ON]->(:Asset|:Service|:Supplier|:Person|:Procedure)

(:Hazard)-[:INITIATED_BY]->(:FailureMode|:CyberScenario)
(:CyberScenario)-[:REACHES]->(:Asset)
(:FailureMode)-[:AFFECTS]->(:SystemFunction)
(:Hazard)-[:MITIGATED_BY]->(:SafetyBarrier|:SecurityControl)
(:SafetyRequirement)-[:ALLOCATED_TO]->(:Subsystem|:Asset|:Procedure)
(:SafetyRequirement)-[:SUPPORTED_BY]->(:CybersecurityRequirement)
(:Requirement)-[:VERIFIED_BY]->(:EvidenceArtifact)
(:Requirement)-[:VALIDATED_BY]->(:ValidationActivity)
(:SafetyCaseClaim)-[:SUPPORTED_BY]->(:EvidenceArtifact|:Requirement)
(:Change)-[:MODIFIES]->(:Asset|:Interface|:Requirement|:Control)
(:Change)-[:TRIGGERS_REVIEW_OF]->(:Hazard|:SafetyCaseClaim|:RiskDecision)
```

## Bottom line

IEC 62278-1 and IEC 62278-2 make the Cyber Digital Twin more valuable because they reinforce the need for a model that is:

- **Multi-level:** System, subsystem, equipment, component, and interface.
- **Lifecycle-aware:** Concept through withdrawal, including modifications.
- **Requirement-traceable:** Operational need through verification and acceptance.
- **Hazard-centered:** Cyber and technical causes linked to safety outcomes.
- **Dependency-aware:** Power, telecoms, supplier, tooling, people, procedures, and recovery.
- **Change-driven:** Every modification triggers visible impact analysis.
- **Assurance-ready:** Claims, evidence, approval, independent assessment, and safety-case relationships remain connected.

That is substantially more useful than treating RAMS as a static PDF set and cybersecurity as a separate vulnerability dashboard.

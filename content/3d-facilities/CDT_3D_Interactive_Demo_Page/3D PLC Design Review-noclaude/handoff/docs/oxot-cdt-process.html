How we build a Cyber Digital Twin

OXOT  OT security engineering

Three phases, two client workshops, three floor walks. The model is built from the client's own documentation, corrected against the physical plant, then loaded with safety and reliability data before any control is recommended. One dataset produces every artifact, so a change in the field propagates everywhere at once.

1BUILD THE MODEL
Inputs
  • High-level design (HLD)
  • Detailed level design (DLD)
  • Interface control document (ICD)
  • OT equipment schedules
  • Descriptions and narratives
What we do
  • Derive the asset list from documentation
  • Establish every connection between assets
  • Classify services — what flows
  • Classify protocols — how it is carried
  • Separate routable from hardwired
Artifacts
  • Asset register
  • Connection graph
  • Service and protocol inventory
  • 3D model of the facility
W1WORKSHOP 1
Inputs
  • The model from Phase 1
  • Client review and corrections
  • Sector threat intelligence
  • Client, equipment and facility profile
  • Geography
What we do
  • Review the model with the client
  • Walk the floor — confirm against as-is
  • Adjust where documents and plant disagree
  • Frame the threat landscape. TS 50701 uses worst case; we apply comparative sector threats through ATQ
  • Mark SIL-rated items
Artifacts
  • As-is corrections
  • Initial SL-T zones and conduits
  • Asset registry, SIL items marked
2LOAD CONSEQUENCE
Inputs
  • Safety team: FMEA, hazard log
  • Safety critical item list
  • Reliability critical item list
  • ConOps
  • Minimum operating requirements
What we do
  • Attach failure modes to assets
  • Build impacts and consequences into the model
  • Encode redundancy from the design, not from feed count
  • Encode MoR thresholds and operating modes
  • Make a pathway traceable to a physical outcome
Artifacts
  • Failure modes on assets
  • Consequence model
  • MoR and operating modes
W2WORKSHOP 2
Inputs
  • Consequence-loaded model
  • TACAM — typical vulnerabilities by equipment class
  • Threat actor profiles from ATQ
  • SL-T from Workshop 1
What we do
  • Show threat actors and pathways on the model
  • Trace to fat-tail loss, critical loss and safety consequence — our own ALE model
  • Review controls the SL-T ratings require, and why, grounded in pathway and consequence
  • Test architectural gaps against ALARP / SFAIRP for a reasonable SL-C
  • Draw the flat network view of the 3D model
Artifacts
  • Threat pathways and consequence
  • SL-C rationale
  • ZCR diagram — zones and conduits
3VERIFY & REPORT
Inputs
  • Samples and configurations
  • SBOMs and HBOMs
  • Switch and firewall configurations
  • SL-C and security requirements by zone
What we do
  • Enter SL-C and requirements per asset by zone
  • Raise model fidelity to the actual facility
  • Walk the floor again with the improved model
  • Gap analysis SL-C against SL-A
  • Build the target reference architecture
Artifacts
  • NOW / NEXT / NEVER report
  • Target reference architecture (IEC 62443)
  • SL-C to SL-A gap analysis
  • Roadmap, priority actions, quick wins
  • Executive readout + long-form report
